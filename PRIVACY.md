# Privacy

DashyNMS does not require a DashyNMS account. Error reports and usage/performance sharing are optional and off until you explicitly allow them.

This document describes DashyNMS 2.0 on Windows, macOS and Linux, and is the source for the [website privacy page](https://dashynms.pckp.net/desktop/privacy/), which says the same in shorter form. Version 1.x shares no error reports or usage measurements.

## Who it talks to

- **Your LibreNMS server**, the one you sign in to. This is where everything you see comes from.
- **Your Graylog and Unimus servers**, only if you set them up in Settings → Integrations.
- **GitHub**, to check for and download new versions of DashyNMS from this repository's [Releases](https://github.com/DashyNMS/desktop/releases), at start-up and every 6 hours. It sends nothing about you or your network, only the ordinary request any download makes.
- **GitHub, for sensor definitions**, which give state readings names and colours. They're on by default and come from the [official repository](https://github.com/DashyNMS/sensor-definitions), or another public GitHub repository you choose, checked at most once a day. The request carries nothing about you or your network. Turn them off in **Settings → Sensor definitions**; applying that removes the downloaded definitions.
- **OpenAI**, only if you sign in to Intelligence with your ChatGPT account. Your questions, and what DashyNMS looks up to answer them (such as device names, addresses, alerts, ports and log lines), are sent to OpenAI under your ChatGPT plan. Passwords, tokens and SNMP communities are never sent. Configuration backups are summarised unless you choose otherwise in **Settings → Intelligence**. If web search is on, OpenAI's search may send search terms to search providers; it can be turned off in Settings. You sign in to ChatGPT in your browser, so DashyNMS never sees your ChatGPT password. Intelligence asks before the first question and again whenever what's sent changes. [OpenAI's privacy policy](https://openai.com/policies/privacy-policy/) covers what it does with them.
- **Sentry**, only for the error reports or usage/performance metrics you choose to share, as described below.
- **OpenStreetMap's tile servers**, for the map backgrounds on the Geographical map, unless your LibreNMS server or Settings names a different tile server. Like any map website, the tile server sees which areas of the map are loaded.

Error and usage reports exclude monitored network data.

**Sign in with LibreNMS** opens your server's own sign-in page inside DashyNMS, using the system's browser engine (Microsoft Edge WebView2, WebKit on macOS, WebKitGTK on Linux). If your server sends you to a single sign-on provider, that provider sees the sign-in as it would in a browser. DashyNMS doesn't read or keep your password; it creates an API token on your server and keeps only that. Each attempt uses a private browser session, so no cookies are left behind.

Alert notifications are created on your computer from DashyNMS's own alert checks and don't pass through any push service. **Report a bug** in **Settings → Diagnostics** opens a GitHub issue in your browser with version details filled in; nothing is sent until you submit it. Showing the **Sign in DashyNMS Mobile** code in **Settings → Server** sends nothing. The code is only drawn on screen for your phone's camera to read.

## Optional error and usage sharing

The first normal launch after this feature becomes available asks for your choice. Both boxes start unchecked. You can allow either category, both categories, or choose **Don't share**. Closing the window leaves sharing off and asks again on the next launch. An explicit choice is remembered. Existing launch-only consent continues to cover launch counts, but never enables broader metrics. Existing broader-metrics consent continues to cover its previous measurements, but does not enable session health. Those users and launch-only users receive an updated prompt with usage unchecked and their error choice preserved. Closing that updated prompt keeps the existing choice and asks again next launch. Existing explicit declines remain declined. Change it in **Settings → Diagnostics**, then apply the change.

- Error reports contain the app version, operating system, processor architecture, time, exception types, and method names from approved application assemblies. Where build symbols are available, they also include repository-relative source file names, line numbers and numeric IL offsets to locate the failing code; async frames use the original method name. They exclude exception messages, absolute/local filesystem paths, log files, network addresses, credentials and Intelligence content.
- Usage sharing sends one `dashynms.app_start` counter measurement per application process after you enable it. It contains the version, operating system, architecture and time. There is no user or installation identifier, so these measurements count launches rather than unique users.

The **Share usage and performance metrics** choice also authorises fixed feature-use counts and measurements of startup, screen loading, request/update outcomes, UI responsiveness and process memory. Individual measurements are added separately; currently launch counts, sampled startup timings, sampled screen-loading durations, API request statistics, UI-stall measurements, coarse feature-use counts, Intelligence request timings/outcomes, update measurements and process-memory gauges are collected automatically. Memory gauges read only this app’s resident working-set size and managed-heap estimate every five minutes, grouped by visible-window or background/tray operation. No memory contents, dumps, process lists, machine names, inventory counts or other applications’ statistics are collected. Update measurements use app source/target versions, release channel and fixed stages/outcomes. A local pending-target marker (at most 1 KiB, seven-day expiry) confirms only that the matching target version later started; launching an installer is not reported as installation success. Withdrawal deletes this marker. A known change from the last running version also identifies an untracked updated startup, without claiming which installation method succeeded. Download URLs and filesystem paths are not included. Intelligence measurements contain only elapsed times and fixed outcome categories; prompts, answers, chat titles, Spotlight objects, tool arguments/results, accounts, model names and credentials are excluded. Feature counts cover opening Maps/Intelligence, entering dashboard edit mode and adding built-in widget types through the picker. Counts are combined locally; custom names, locations, object IDs and individual navigation histories are excluded. UI-stall measurements count foreground dispatcher delays of at least 500 ms and sample their duration. A one-second heartbeat keeps at most one pending callback; detected sleep/scheduling gaps, background operation and debugger-attached intervals are excluded. No screenshots, frame contents or user input are captured. API statistics contain only a built-in operation category (device list, alerts, sensors or other), outcome counts and sampled elapsed durations. Retries/failover are included in a single logical request; URLs, HTTP headers and request/response content are excluded. Screen loads use built-in view categories and cached, success, failure or cancellation outcomes, without screen titles or identifiers. Startup timing covers managed application startup until the first window is ready (or the tray is ready for a hidden start), excluding initial session restoration. It is recorded for a random one in ten launches with metrics consent already in place. No prompts, answers, tool arguments/results, free text, device/server identifiers, request URLs or payloads, memory contents or machine names are included. Measurements describe the participating reporting population, not all installations.

Session health requires **both error and usage sharing under the updated choice**. It records a fresh random ID for each eligible process interval, its app version/platform and one terminal outcome: healthy, errored, known managed crash, or abnormal/unknown. Foreground and tray time belong to the same interval; restart starts another. Enabling both choices midway starts an interval then, without collecting earlier activity. Duration is sampled for a random one in ten intervals. There is no persistent user or installation ID, and these measurements cannot count unique users or retention.

An observed command/UI error followed by normal exit is errored; a managed exception reaching the process's unhandled-exception hook is a known managed crash. A missing exit marker, forced termination, native crash or power loss is abnormal/unknown on the next eligible launch, never automatically a confirmed crash. Unknown outcomes have no duration. A session still running, never restarted or lost to queue limits is absent from the terminal counts. Any managed crash-free percentage uses only known-ended intervals from this same both-choice population, excluding abnormal/unknown outcomes, and does not measure all crashes or all installations.

Recovery uses a sanitised `session-health.json` marker of at most 2 KiB, with seven-day recovery expiry. It contains only the fresh interval ID, times, safe app/platform context, sampling/error flags and any known terminal outcome. Withdrawing either choice deletes the marker and queued session reports. Other separately allowed usage measurements continue. No native crash dumps or memory contents are collected.

Broader counters are aggregated locally; durations retain the first observation and every tenth observation per built-in series. At most 32 points are buffered and batches are persisted every minute or on a normal exit. Abrupt exit can lose the in-memory tail. Metrics uploads are limited to one request per minute, with additional backoff for failures and server limits. Capacity limits, local persistence failures and expiry can drop observations; retries can duplicate them. Counts are approximate, and sampled durations are not a complete record of activity.

Usage/performance measurements use Sentry Application Metrics, separately from error events. Metrics ingestion requests disable IP and user-agent inference.

Sentry receives the connection information necessary to accept a report, including its source IP address. Reports are therefore not described as anonymous. The configured project uses Sentry's EU ingestion endpoint. See [Sentry's privacy policy](https://sentry.io/privacy/) for its handling of service data.

Consented reports can wait locally in the application's `crash-reports` directory while offline. The queue holds at most ten reports of at most 32 KiB each and expires them after seven days. Disabling a category cancels its pending delivery and deletes its queued reports. This does not remove reports already received by Sentry. Server retention follows the Sentry project's configured retention policy.

Fatal managed errors are saved for delivery on a later launch. Native crashes and memory dumps are not sent. Demo and screenshot modes do not report. Local diagnostic logs are separate and are never attached to these reports.

## What's kept on your computer

Everything DashyNMS saves stays on your computer, in your user account: your server address and settings, dashboards and map layouts, any certificate you've chosen to trust, saved Intelligence chats, downloaded updates, queued reports waiting to be sent, and log files kept for 14 days. Map tiles are cached for a week.

| | Settings, chats, logs and updates | Map tiles |
| --- | --- | --- |
| Windows | `%APPDATA%\DashyNMS` | `%LOCALAPPDATA%\DashyNMS` |
| macOS | `~/Library/Application Support/DashyNMS/avalonia` | `~/Library/Application Support/DashyNMS/tiles` |
| Linux | `~/.config/DashyNMS/avalonia` | `~/.local/share/DashyNMS/tiles` |

Your LibreNMS API token, Graylog password, Unimus token and Intelligence chats are encrypted for you. On Windows, Windows does this (DPAPI) for your Windows account. On macOS and Linux, DashyNMS uses a key kept in your login Keychain or your keyring (the Secret Service, such as GNOME Keyring or KWallet). You can turn off saving the LibreNMS token entirely. Sensor definitions are kept with the installation.

**Signing out removes all of it** apart from the logs and downloaded updates, and DashyNMS restarts ready to sign in again. On Windows, uninstalling asks whether to remove these folders too. Keep them and a reinstall picks up where you left off; a silent uninstall always keeps them. On macOS and Linux, removing the app leaves them in place; the [user guide](docs/guide/reference/your-data.md) explains how to remove them.
